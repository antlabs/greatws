# fio vs fnet 压测记录

测量环境：Intel Ultra 9 275HX（8 个 P 核 5.3-5.4GHz + 16 个 E 核 4.7GHz，共 24 逻辑核），
lab 机 192.168.1.99，C++ 客户端 `benchcli-uwscpp`，10000 连接 / 1024B 消息。
CPU governor 固定 performance。

**测量精度说明**：同一配置 6 轮交替实测，quicknet 自身波动 2.97%、fnet 0.82%
（见第四节）。**1% 级别的差异在本机测不出来**，下表里小于 3% 的差距都要按噪声看。

### 3.5 建连路径

**隔离测量**（服务端刚启动、无历史负载，`-en 200000`）：

| 实现 | Connections TPS | Used |
|---|---|---|
| quicknet（net/http 路径） | **67,996** | 147.07ms |
| **fnet** | 67,718 | 147.67ms |
| quicknet（rawtcp 自建 accept） | 59,010 | 169.46ms |

**在干净条件下 quicknet 略快于 fnet（+0.4%）**。官方三件套里那 -13.5% 是在
客户端预热 12 秒、10000 连接已建立后的稳定态测到的，条件不同；这一项受
当时的机器负载影响很大（见第四节的噪声数据）。

另外测过：rawtcp 自建 accept 路径**始终更慢**（单 goroutine accept 串行化，
而 net/http 的 50 个 listener 天然并行），已弃用。

握手解析开销：**864.5ns / 1408B / 29 allocs → 216.8ns / 224B / 1 alloc**（改后，
虽然整条 rawtcp 路径不用了，但这个重写本身是对的）

### 3.6 读路径去锁（受控交替 A/B，L2/P10，8 P 核）

原来 `socketRead` 前后持 `c.mu`。但那把锁保护的是写缓冲 `wbufList`，
读路径只碰 `rbuf/rr/rw`，两者没有共享数据——原来的写法让每条消息的读写
互相串行（回调里 `WriteMessage` 持锁走完整个 sendto，期间读只能等）。
fnet 的读路径一把锁都不加。

交替跑两个二进制（唯一差别就是这把锁）：

| 轮 | 有锁 TPS | 无锁 TPS | 有锁 TP99 | 无锁 TP99 |
|---|---|---|---|---|
| 1 | 1,385,933 | 1,388,618 | 17.24ms | **17.06ms** |
| 2 | 1,388,137 | 1,383,861 | 17.52ms | **17.02ms** |
| 3 | 1,389,561 | 1,387,432 | 17.47ms | **16.94ms** |
| **均值** | **1,387,877** | **1,386,637** | **17.41ms** | **17.01ms** |

**TPS 差 0.09%（零）；TP99 稳定好 2.3%（三轮全赢）；CPU 无差异。**

结论：这把锁在 echo 下几乎从不竞争（每个连接只被一个解析 goroutine 碰，
总是走无竞争快速路径），去掉它对吞吐没有可测影响，只让尾延迟稳一点。
race detector 全绿（说明它确实没保护任何被并发访问的数据）。

| | TPS | task-clock（6s 窗口） | read 次数 | write 次数 |

**syscall 次数严格相等（1 读 1 写，逐条对齐）**，但 fnet 用少 5.6% 的 CPU

## 六、被证伪的假设

| 假设 | 实测结果 | 结论 |
|---|---|---|
| 闭包逃逸分配在关键路径上 | 关掉 GC 后 TP95/TP99 不动 | 不在 |
| 每消息原子计数是瓶颈 | 开关对比无差异 | 无影响 |
| 每分片单执行体没余量是根因 | 多 worker + scheduled 位调度实现后，曲线不变 | **不是** |
| 读缓冲大小影响 syscall 成本 | 2/8/16 倍无差异 | 无影响 |
| 超订可以换吞吐 | 26 个 goroutine 是最优点（= 库默认） | 已是默认 |
| `parseInEventLoop` 全内联更快 | 1.52-1.57M，不如接池 | 否 |
| rawtcp 自建 accept 更快 | 两次都更慢（71,195 / 67,932 vs 75,526） | 否 |
| P/E 核异构是次要因素 | 分开绑定后波动从 2.97% 降到 <1% | **是噪声主因** |
| 413 线程 vs 13 线程有 CPU 代价 | 非自愿上下文切换几乎相同（7350 vs 7872） | 无代价 |
| 用 fnet 的协程池能更快 | 慢 12%（多一跳跨 goroutine） | 否 |

## 七、代码改动与实测收益

| 改动 | 实测收益 | 状态 |
|---|---|---|
| `pulse` 两段式 park 等待 | park 模式吞吐从落后 3% 恢复到平手 | 有效 |
| 零拷贝 payload（`WithServerZeroCopyPayload`） | 1024B: +1.3% TPS / -2.5% CPU；16KB: -2.3% CPU | 有效，默认关 |
| `Conn` 字段重打包（保 216 字节不变，腾出 4 字节原子位） | 基础设施，解锁连接级调度 | 有效 |
| `scheduled` 位 + pending 事件（fnet 式连接级调度） | 实现后曲线不变 → 排除了最后一类假设 | 有效（结论为负） |
| `WithParseWorkersPerShard`（多 worker 分片） | +11% TPS，但 TP95 翻倍 | 默认 1（= 旧行为） |
| 握手解析零分配重写 | 864.5ns/29 allocs → 216.8ns/1 alloc | 有效 |
| 读路径去锁（`socketRead` 不再持 `c.mu`） | TPS 无变化，TP99 稳定好 2.3% | 有效（小幅） |
| **bug①** `addTask` 闭包致 `f` 逃逸进堆 | 分配 684MB，不在关键路径 | 修复 |
| **bug②** `leftMove` 会搬走回调正在读的数据 | 零拷贝路径上的内存错乱 | 修复 |
| **bug③** `takePending` 清 `scheduled` 开了并发窗口 | 两个 worker 同时碰一个连接 → SIGSEGV | 修复 |
| **bug④** `processOne` 错误退出不清 `scheduled` | 连接永久卡死 | 修复 |

## 九、测量陷阱（这几条害我给出过错误结论）

1. **残留进程占端口**：有一次一个 `quicknet_event.server` 一直活着占着
   15901-15950，客户端连的是它，新起的进程接不到连接。那次以及之后十几次
   测量全废，我一度得出"TPS 掉到 475K、CPU 只有 106%"的错误结论。
   **每次跑之前必须 `ss -ltn` 确认端口没被占。**

2. **P/E 核异构**：12 核混合绑定（0,2,4,…,22）下我们自身波动 2.97%，
   fnet 0.82%；分开绑定到纯 P 核后两边都降到 1% 以内。**判定必须在同构核上做。**

3. **Connections 的噪声最大**：同一实现测出过 63,082~96,109（52% 跨度），
   fnet 也测出 60,065~123,920（106% 跨度）。**这一项单次测量没有任何意义。**

4. **同配置跨轮矛盾**：6L/40P park 两次测量得到 -0.25% 和 +1.67%，符号相反。

## 十、Profile 驱动的优化：writev（本轮主要进展）

**流程：先 profile → 定位 → 改 → 验证。**

profile 显示（8 P 核，1KB echo）：

| | quicknet |
|---|---|
| `Syscall6`（内核态） | **92.1%** |
| 写路径 cum | **67.05s**（57%） |
| 读路径 cum | 33.76s（28%） |

**写是读的两倍** —— 定位到 `frame.WriteFrame`：它每消息从池取一块 buf、
把 header 写进去、**把 payload memcpy 进去**、再整块写 socket。

**改动**：新增 `socketWritev`（`sendmsg` + iovec），header 在栈上构造、
payload 零拷贝；服务端 + 未压缩 + ≤65535 字节时走这条路。

**验证（8 P 核，6 轮交替，噪声 0.13%）：**

## 十一之二、第二轮 profile 驱动的改动

继续对 profile 挖，发现三处"慢路径混进热路径"：

| 位置 | 问题 | 改动 | 实测（8 核，3 轮全赢） |
|---|---|---|---|
| `waiter_linux.go` | `syscall.EpollWait` 走 `Syscall6`（带 entersyscall/exitsyscall） | 换 `RawSyscall6` 版 | TPS +0.52%、TP95 -2.3%、TP99 -4.5% |
| `api_epoll.go` | 同上（非 park 路径） | 同上 | — |
| `api_epoll.go` | `syscall.EpollCtl` 走 `Syscall6` | 换 `RawSyscall6` 版 | TPS +0.34%、TP95 -2.8% |
| `conn_unix.go` | `errors.Is(err, EAGAIN)` 每消息展开 error 链 | 断言 `syscall.Errno` 直比 | +0.3%（方向一致） |
| `processWebsocketFrame` | 乘数走 float32 转换 | 改整数（**无收益，已回退**） | — |
| `rbuf` 生命周期 | 想跨消息缓存（省 GetBytes 2.1%） | **崩溃，已回退** | — |

**profile 的最终分布（8 P 核，1KB echo）：**

```
Syscall6 (内核态)          91.8%   ← 改不动
Mutex.Lock/Unlock           0.74%
bytespool.GetBytes/PutBytes  0.18%   ← 不是瓶颈(之前误读成 2.1%)

```

## 十一之五、无绑定环境 TP99 那 1ms 的最终诊断

无绑定环境下我们 TPS 领先 5%、TP99 落后 7.6%（绝对差 1ms）。排查过的：

| 假设 | 实验 | 结果 |
|---|---|---|
| 解析 goroutine 不够 | 40 / 80 / 120 | 无差异（TP99 都在 14.6~15.4ms） |
| 投递阻塞 | `/shards` 诊断口 | `blocked` 全 0 |
| 分片倾斜 | 同上 | 均匀（每分片 248~251 个 fd） |
| 绑核 | `WithParsePinned`（LockOSThread） | 无差异 |
| 事件循环数 | 6 / 12 / 24 | 无差异 |
| 唤醒机制 | 试过 runtime 信号量；查证 fnet | **fnet 也用 channel，不是差异源** |
| 让出 P（gosched） | off vs on | on: TPS +3.5%、CPU -6.6%、**但 TP99 +7.7%** |

**根因（在 fnet 的 taskpool 源码里找到）**：

```go
for task := s.pop(); task != nil; task = s.pop() {
    if s.hasTask() {     // 队列里还有活
        s.notify()       // ← 先叫下一个 worker 来, 再处理手上这个
    }
    run(task)            // ← 这样当前任务耗时也不挡住后面的
}
```

fnet 是**多 worker + 逐跳唤醒**：队列里还有任务时先唤醒下一个 worker，
再跑手上的。而 quicknet 是**分片单 worker**：处理完一个才取下一个，某个
任务慢（比如回调里 WriteMessage 撞上 EAGAIN 要重试）时，同分片的其他
连接全在等。

**这是架构建模的差异，不是可以打补丁消除的点。** 我们试过加 worker
（`WithParseWorkersPerShard`），但那是"提前起更多 goroutine"，
在无绑定环境下没有帮助；fnet 的机制是"按需唤醒 + 逐跳传播"。

要真正对齐，需要把"分片单 worker"改成"任务池 + worker 按需伸缩"，
也就是重构 `task_parse.go` 的调度模型。之前验证过"挂 fnet 的池"会慢
12%（多一跳跨 goroutine），所以这需要重新设计而不是直接复用。

## 十二之二、三方同会话交替（判定"谁快"的唯一可靠办法）

之前所有"谁快"的结论都不可靠，因为 fnet 自己的读数在不同会话间漂 9%
（1.985M ↔ 2.181M）。唯一可靠的做法是同一时段内交替。

无绑定，4 组，每组 fnet / gw(parse=40) / gw(parse=20) 依次跑：

| | fnet | gw parse=40 | gw parse=20 |
|---|---|---|---|
| **TPS** | **2,183,663** | 2,094,331（-4.1%） | 2,045,858（-6.3%） |
| Avg | **4.46ms** | 4.68ms | 4.81ms |
| **TP95** | 11.61ms | 10.92ms（-5.9%） | **10.49ms（-9.6%）** |
| **TP99** | 16.77ms | 14.94ms（-10.9%） | **14.15ms（-15.6%）** |
| CPU | **1008.1%** | 1122.1% | 1190.6% |

4 组方向完全一致。

**但换个机器状态结果就翻**：早前几轮 fnet 跑 2.0M 时，我们的 TPS 是
+5.7% 领先、TP95 落后 3%。这轮 fnet 跑 2.18M，变成我们 TPS 落后 4.1%、
延迟领先 6~16%。

**所以"谁快"的准确回答是**：

| 机器状态 | TPS | 延迟 |
|---|---|---|
| fnet 跑 2.0M 时 | quicknet +5.7% | fnet 好 3% |
| fnet 跑 2.18M 时 | fnet +4.1% | **quicknet 好 6~16%** |

**TPS 上互有胜负（取决于机器状态），而我们的读数稳定、fnet 的漂。**
延迟这一项在当前机器状态下我们全面领先，`parse=20` 更是把 TP95 压到
10.49ms（比 fnet 低 9.6%）。

## 十二之三、无绑定 TPS 那 4% 的排查

`十二之二` 那轮 fnet 跑 2.18M、我们 2.09M(差 4.1%), 于是查这 4% 在哪。
注意 fnet 那轮 CPU 只用 1008% 而我们用 1122%——**我们多花 CPU 却吞吐更低**,
说明不是"CPU 不够", 是"CPU 花得不够有效"。

试过的:

| 假设 | 实验 | 结果 |
|---|---|---|
| 事件分发不够快 | 事件循环 6/12/24（每档配 fnet 锚点） | TPS 2.09~2.10M、TP95 10.9~11.1ms, **三档无差异** |
| 解析侧不够 | 解析 goroutine 20/26/32/40/80/120/240 | 只有取舍(见十一之九), 没有净改善 |
| 任务排队 | 多 worker + 逐跳唤醒 | 无差异 |
| 调度饥饿 | GODEBUG=schedtrace + gosched | runq 堆积与 gosched 无关 |
| 唤醒慢 | 自旋(procyield) | **-74.7% TPS** |
| 队列深度 | 分片数 40/120/240 | 等待分布不变 |
| GOMAXPROCS | 12/14/16/18/20/24 | 单调取舍, 24 尾延迟最优 |

**七个假设全部排除。** 那 4% 不是某一处慢, 而是整条链上每一处都多花一点
CPU（我们 1122% vs 1008%）——而 CPU 花得多, 在饱和机器上又变成更长的等待。
这是"效率换延迟"的同一个取舍的两个面。

## 十四、Pipeline 的三处优化（profile 驱动，本轮）

起因：Pipeline 那张表里 quicknet 一直不是第一。先把两边的 profile 抓下来
（`-rp` 让客户端采服务端的 pprof），差别全在写路径：

| 10 秒窗口 | quicknet | fnet |
|---|---|---|
| 总样本 | 66.11s (660%) | 28.60s (286%) |
| 写路径 cum | **43.12s** | 12.81s |
| 读路径 cum | 12.82s | 9.80s |

那次两边 TPS 都顶在客户端上限（200×10000=2,000,000），判定列是 CPU EER，
所以"fnet 用一半 CPU 拿同样的吞吐"就是要解决的问题。三处改动：

### 14.1 攒包（cork）：写系统调用 2,000,000/s → 200,000/s

客户端一次 write 带一批消息（`-rpl` 10~15），服务端每条回一次 write。
抄 fnet 的 cork/uncork：解析到一个 frame 后如果读缓冲区里还有没解析的
字节，就开攒（`cork.go`）；回调里写出去的消息先进 `wbufList` 那块缓冲区；
整轮 read 结束时一次写出；装不下时 `writev` 直接把 payload 带过去（不拷）。

服务端自己记的计数（A 配置，1 秒稳态）：

```
改动前: read_syscalls +2,000,000/s   write_syscalls +2,000,000/s
改动后: read_syscalls +2,000,000/s   write_syscalls +200,000/s
```

### 14.2 自适应读缓冲区：读系统调用 2,000,000/s → 200,000/s

读缓冲区按上一条消息的 payload 算（约 1 条 1KB）。一批 15 条进来时内核
把整批给它，它只解析出一条，剩下的留在 socket 里——而 ET 的边缘是"新数据
到达"触发的，那些剩余数据不产生新边缘，只能等下一次事件，于是变成一条
消息一次 read（正好 2,000,000/s）。

改法：一次 read **把缓冲区读满**（`c.rw == len(rbuf)`，说明后面还有）就
换成 16KB 的大块，下一批一次读完。这个信号是准确的——Echo 那种"一次 read
一条"的连接永远读不满，就一直用小块。

```
改动后: read_syscalls +200,000/s（和写一样，每批一次）
```

**先做过无条件 16KB 的版本**：Pipeline 一样快，但 Echo 慢 0.46%（3 轮
一致，10000 连接 × 16KB = 160MB 的常驻代价）。改成按需增长后 Echo 回到
+0.16%（3 轮）。

### 14.3 去掉积压写完后的空转 epoll_ctl

`write()` 里积压写完会 `ResetRead`（一次 `EPOLL_CTL_MOD`）。但 ET 下
`AddRead` 注册的就是 `EPOLLIN|EPOLLOUT|EPOLLET`（pulse 的 `etAddRead`，
照抄 man 手册里 ET 那条用法），`AddWrite` 是空操作，`ResetRead` 注册的
掩码和 `AddRead` **完全一样**——这次 MOD 什么都不改，只是陷进内核一次。

```
epoll_ctl 占 9.21s / 33.25s 系统调用时间（10 秒 profile）
```

只有背压（`flowBackPressureRemoveRead`）那条路真的删过读事件，它还需要
这次 ResetRead。

### 顺带修的

- `socketWritev` 出错时返回 `int(n)`，而 `n` 是内核放在返回值里的
  `-errno`，调用方拿这个负数去切 slices 会 panic。`WriteMessage` 那条
  writev 路本来就有这个雷，攒包这条路新踩到；现在统一返回 `0, errno`
  （和 `socketWrite` 一致），`corkWrite` 里也加了兜底。
- 测试里直接调 `con.write()` 要自己拿 `c.mu`（它和 `WriteMessage` 一样
  要求调用方持锁），否则和服务端的 flush 竞争——这是测试写法问题，
  不是库的 bug。
